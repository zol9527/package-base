# Feature Specification: RBAC 权限管理与资源访问控制

**Feature Branch**: `002-rbac`  
**Created**: 2025-10-10  
**Status**: Draft  
**Input**: User description: "我已经实现了登录，现在我想实现 rbac 权限管理，对账号施行权限的资源控制"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 为账号分配角色并强制访问控制 (Priority: P1)

作为系统管理员，我可以将一个或多个角色分配给账号，使该账号仅能访问被授权的资源与操作；未授权的请求被拒绝并给出友好提示。

**Why this priority**: 没有授权控制则存在越权风险，属于安全与合规最核心能力。

**Independent Test**: 创建用户并赋予“只读”角色；验证其可访问GET类资源但无法进行POST/DELETE；将角色切换为“管理”，验证写入操作被允许。

**Acceptance Scenarios**:

1. Given 账号A拥有“只读”角色，When 访问受保护资源的读取操作，Then 返回成功且数据可见。
2. Given 账号A拥有“只读”角色，When 尝试写入/删除受保护资源，Then 返回未授权（403），响应含原因码；审计日志记录拒绝。
3. Given 管理员为账号A新增“管理”角色，When 账号A再次发起写入，Then 返回成功；审计日志记录允许。

---

### User Story 2 - 自定义角色与精细化权限 (Priority: P2)

作为系统管理员，我可以创建自定义角色，选择资源范围（支持命名空间与通配符）和动作（如 read/write/delete/manage），并将该角色分配给账号。

**Why this priority**: 企业通常存在按域拆分的细粒度访问控制需求，需适配不同团队与职责。

**Independent Test**: 创建“Billing-ReadOnly”角色（资源：billing.*，动作：read），分配给用户；验证GET账单成功，POST账单被拒。

**Acceptance Scenarios**:

1. Given 创建自定义角色R并配置资源=“billing.*”、动作=“read”，When 分配给用户U，Then U可读取任意账单资源。
2. Given 用户U已分配角色R，When 尝试在billing域执行写入或删除，Then 返回403并给出提示“缺少写入权限”。

---

### User Story 3 - 审计与可追溯性 (Priority: P3)

作为安全审计员，我可以查看近30天的访问决策记录（允许/拒绝）、筛选用户/资源/动作/时间范围，支持导出用于合规审计。

**Why this priority**: 需要在事后追踪越权尝试与策略效果，降低合规风险。

**Independent Test**: 制造若干成功/失败访问请求，进入审计视图筛选并导出，核验记录完整性与字段准确性。

**Acceptance Scenarios**:

1. Given 存在多条允许/拒绝记录，When 按用户和资源过滤，Then 仅显示符合条件的记录。
2. Given 审计员选择导出，When 下载完成，Then 文件包含所选时间窗内的决策明细与统计摘要。

---

### Edge Cases

- 用户未分配任何角色时访问受保护资源：默认拒绝（403），提示“未授权访问”。
- 角色被撤销或权限变化后：变更应立即生效（强一致），所有后续请求立刻按最新权限评估；进行中的请求不回溯调整结果。
- 同时存在允许与显式拒绝策略：显式拒绝优先于允许（Deny overrides Allow）。
- 资源匹配冲突（具体资源与通配符并存）：更具体的资源规则优先于通配符。
- 被禁用/锁定账号即便具备角色也应拒绝访问（账号状态优先）。

## Requirements *(mandatory)*

### Functional Requirements

- FR-001: 系统必须对所有受保护资源实施“默认拒绝”，仅在显式授权存在时才允许访问。
- FR-002: 系统必须支持“角色-权限”模型；角色可包含多个权限，权限由“资源标识+动作+效果(允许/拒绝)”构成。
- FR-003: 系统必须提供内置基础角色：管理员(Admin)、管理(Manager)、只读(Viewer)；允许启用/禁用内置角色分配。
- FR-004: 系统必须支持角色的创建、更新、删除，以及将角色分配/解除分配到账号。
- FR-005: 系统必须支持资源命名规范（如 域:子域:标识），并支持通配符匹配（如 billing.*、project:*）。
- FR-006: 系统必须在鉴权失败时返回403；在未认证时返回401；错误消息面向用户友好且不泄露敏感策略细节。
- FR-007: 系统必须记录访问决策日志（允许/拒绝、用户、资源、动作、时间、请求标识、决策原因），供审计查询与导出。
- FR-008: 系统必须提供确定性的策略评估顺序：显式拒绝 > 最精确匹配 > 通配符匹配；若仍未命中，默认拒绝。继承聚合后的权限按同一顺序评估；任一层级的显式拒绝均优先。
- FR-009: 系统必须提供接口/能力以查询账号的“有效权限”（可选过滤资源与动作）。
- FR-010: 系统必须支持按“范围/作用域”进行角色绑定（如未来扩展到项目/组织维度），若无范围则默认为全局作用域。
- FR-011: 系统必须确保账号状态（禁用/锁定）优先于授权结果，处于失效状态的账号被拒绝访问。
- FR-012: 系统必须提供最小权限原则的配置指引和默认策略示例，以降低误配风险。
- FR-013: 权限与角色变更必须“立即生效”，后续请求在变更提交后即按最新策略评估；若存在缓存，应确保对授权判定的可观察一致性和回滚策略。
- FR-014: 系统应支持导出/导入角色与权限配置，以便备份与迁移（可作为后续增量）。
- FR-015: 本版本为单租户范围；需为未来的多租户强隔离预留设计说明（策略、角色、绑定、日志的租户维度与隔离要求）。
- FR-016: 角色支持继承/包含关系：上位角色可包含下位角色的权限集合；在聚合权限时，显式拒绝优先于允许；循环继承必须被禁止并在配置时校验。

### Key Entities *(include if feature involves data)*

- 角色（Role）：名称、描述、是否内置、是否启用、创建/更新信息、父角色集合（可选，用于继承）。
- 权限（Permission）：资源标识（命名空间路径）、动作（read/write/delete/manage 等）、效果（allow/deny）、备注。
- 角色-权限映射（RolePermission）：角色ID、权限集合。
- 账号-角色绑定（UserRoleBinding）：账号ID、角色ID、作用域（可选）、到期时间（可选）、创建/更新信息。
- 访问决策日志（AccessDecision）：用户标识、资源、动作、是否允许、理由（命中规则/默认拒绝）、时间戳、请求ID、客户端信息（可选）。

### Assumptions & Scope

- 本版明确为单租户（Single-tenant）；未来版本可引入多租户并在策略/日志等处强隔离。
- 默认角色集合为 Admin/Manager/Viewer，可在后续版本扩展更多模板角色；Admin 可继承 Manager/Viewer（示例），具体继承关系可在内置角色说明中定义。
- 资源命名采用“域:子域:标识”的约定式规范；未指定子域/标识时可用“*”通配。
- 范围/作用域（Scope）为可选能力，用于未来按项目/组织等维度收敛权限。
- 非功能性范围：本版本不包含UI设计细节与具体技术实现，仅定义业务行为与约束。

### Acceptance Criteria (Summary)

- AC-001 (FR-001): 对任一受保护端点，在未命中任何允许规则时必须返回403；安全测试用例验证默认拒绝。
- AC-002 (FR-002/FR-004): 可创建角色并配置至少一种权限；分配后立即对后续请求生效；撤销后随即拒绝先前允许的操作。
- AC-003 (FR-005): 资源标识支持“域:子域:标识”与通配符；用例验证具体规则优先于通配规则。
- AC-004 (FR-006): 未认证返回401，已认证但未授权返回403；响应含标准化错误码与人类可读提示。
- AC-005 (FR-007): 任一授权判定（允许/拒绝）均在日志中可查询到包含用户、资源、动作、时间、决策原因的记录。
- AC-006 (FR-008): 当存在显式拒绝与允许冲突时，拒绝优先；继承聚合后评估顺序保持确定性。
- AC-007 (FR-009): 可查询账号在给定资源/动作下的有效权限，返回包含来源角色与规则的概览。
- AC-008 (FR-010): 在存在作用域时，仅在匹配作用域内生效；无作用域则全局生效。
- AC-009 (FR-011): 账号被禁用/锁定后，任一受保护操作返回403；日志记录状态原因。
- AC-010 (FR-013): 变更角色/权限配置后，新请求立即按新策略评估；测试验证无>0秒的可见延迟。
- AC-011 (FR-015): 文档中提供多租户预留与隔离设计要点，但实现与测试以单租户为准。
- AC-012 (FR-016): 定义继承关系后，上位角色自动具备下位角色权限；禁止循环继承的校验用例通过。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- SC-001: 100% 受保护端点均在授权控制下，未授权请求不会泄露敏感数据。
- SC-002: 具备权限的合法请求，95% 在1秒内完成（端到端从发起到响应）。
- SC-003: 管理员创建角色并完成分配的全流程，90% 情况下可在30秒内完成。
- SC-004: 上线后首月与权限相关的支持工单较基线下降50%，误配引发的越权事件为0。
- SC-PERF: 鉴权与授权判定对常规请求的时间开销可感知度低（用户主观感知为“几乎即时”）。
- SC-CONSISTENCY: 新增接口的响应结构符合统一规范，合规率达到100%。
- SC-TEST: 新增功能代码的总体覆盖率≥70%，涉及安全关键路径（策略评估、决策分支）覆盖率≥90%。
